其他常见的验证码漏洞

验证码的弱点不只有"图片太简单、可被 OCR 识别"一种。下面这些变体在真实系统里同样高频出现，成因与危害各不相同，测试时应逐项确认。

  • 验证码回显
    原理：服务端生成验证码后，把答案明文一并写进响应——包括响应体、JSON 字段、Cookie、隐藏表单域，或前端 JS 变量、注释、接口返回。
    危害：攻击者不用识别图片就能直接拿到答案，人机校验形同虚设，可全自动爆破、批量注册或刷接口。
  • 验证码不过期 / 可重复使用
    原理：验证码没有设置有效期，或校验通过后未从会话中销毁；刷新页面、重复提交同一验证码仍然有效。
    危害：抓到一次有效验证码后可长期复用，配合字典即可完成自动化爆破。
  • 验证码可爆破
    原理：验证码字符集小、位数短（如 4 位纯数字），且校验接口没有次数限制、频率限制或失败锁定，攻击者可枚举报空间。
    危害：即使图片不能被 OCR 识别，也能通过枚举绕过；还会放大撞库、短信轰炸等风险。
  • 不区分大小写
    原理：服务端校验时统一转成小写或大写再比较，实际有效组合只剩一半甚至更少。
    危害：可用空间被人为缩小，爆破成本显著下降。
  • 未绑定会话 / 用户
    原理：验证码只按"值"校验，不校验它属于哪个 Session、账号、手机号或 IP；换一个会话、换一个账号仍能通过。
    危害：攻击者可以自建会话批量获取验证码答案，再拿到目标账号上使用，形成"验证码池"绕过。
  • 客户端生成或校验
    原理：验证码在浏览器端生成，或仅由前端 JS 判断是否正确，服务端不校验。
    危害：直接改包或禁用 JS 即可绕过，防机器人能力为零。

本实验的侧重点

本实验主要演示的是「验证码可 OCR 识别」漏洞：验证码图片本身样式过于简单，可被 ddddocr 等机器识别，从而绕过人机校验。上面其他变体仅作知识补充，本关卡未逐一复现。

漏洞描述

验证码用后即销毁只能防"复用"，但如果验证码本身样式过于简单（白底黑字、固定字体、低干扰），攻击者可借助 OCR 工具或 Burp 插件自动识别每张新验证码，再配合字典完成自动化爆破。这类问题属于"验证码强度不足 / 可被 OCR 识别"。

漏洞危害

可被 OCR 识别的验证码形同虚设：攻击者用 ddddocr 等识别库把图形验证码还原为文本，再配合 Burp 插件实现全自动爆破，验证码的防暴破作用完全失效。后果与没有验证码相同——批量撞库、账号接管、短信/邮件接口被恶意刷量；更糟的是企业会因"已上验证码"的纸面合规而误判真实风险。

挖掘技巧与经验

  • 验证码是否一次性：正确输入一次后，再用同一验证码提交第二次，看是否仍然有效。
  • 验证码强度：背景是否纯色、字符是否旋转/扭曲、干扰线/点密度、字体是否固定。
  • 验证码是否可被 OCR 识别：把 captcha_code.php 图片下载下来用 ddddocr / Tesseract 识别，看能否稳定还原。
  • 识别流程：每次请求前先 GET 验证码图片 → OCR 提取 → 带着 captcha POST 登录。
  • Burp 可用 OCR 插件（如基于 ddddocr 的插件）在 Intruder 中自动识别并填充 captcha 字段。

社工字典

  • 思路：通用 top1000 命中率有限，按目标"定制"的社工字典成功率更高——围绕企业信息批量生成变体。
  • 域名变体：取域名主体（如 example.com → example）组合：example123、example@2026、Example#2026、example.com@123。
  • 组合规则：公司名/品牌名/项目名 + 年份(2024-2026) + 特殊字符(@#!_)，再做大小写与前后缀轮换。
  • 扩展素材：员工姓名拼音、工号、手机号、生日、部门缩写、产品线名。
  • 生成工具：CUPP、pydictor、亦幻社工字典生成器等，输入关键词即可批量产出变体字典。
