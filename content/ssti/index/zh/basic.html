为什么要使用模板引擎

模板引擎的核心价值是把「页面长什么样」和「数据怎么算」分开：开发者只写带占位符的模板，业务代码负责准备数据，渲染时再把两者拼起来。这样做带来四方面收益：

  • 视图与逻辑分离：HTML 结构交给前端或运营维护，PHP 只处理数据与流程，改版式不必动业务代码，多人协作边界清晰。
  • 复用与继承：页头、页脚、侧边栏可以抽成公共片段，子模板通过 include / extends / block 复用，避免每个页面复制一份相同 HTML。
  • 自动转义与安全：Twig、Blade、Jinja2 等默认对输出做 HTML 转义，能挡住大部分反射型 XSS；同时提供沙箱与白名单，限制模板能访问的对象和方法。
  • 渲染效率与多端输出：模板可编译缓存，重复渲染更快；同一套模板还能输出 HTML、邮件、报表乃至 PDF 等多端内容。

问题也正出在「模板要执行语法」这一点上：引擎必须解析 {{ }}、{% %} 里的内容。如果应用把用户输入直接拼进模板再交给引擎渲染，用户输入就不再是数据，而会被当成模板代码求值——这就是 SSTI。是否安全，取决于引擎是否把「数据」和「模板」严格分开：成熟引擎通常要求模板来自可信文件，用户输入只作为变量值传入；自研或错误用法把用户输入当作模板源码，风险便随之出现。

漏洞描述

SSTI（Server-Side Template Injection，服务端模板注入）指用户输入被拼进模板后，被模板引擎当作代码而非数据渲染。攻击者一旦能控制模板语法，往往可以直接触达底层语言运行时 —— 在 PHP 里通常意味着任意函数调用、任意文件读取，直至系统命令执行。

漏洞危害

SSTI 的危害直接等同于代码执行：模板引擎本就能访问应用内部对象，注入模板语法后可读取配置密钥与环境变量、调用危险函数，最终通过模板表达式执行系统命令拿下服务器。渲染发生在服务端，前端无任何异常迹象，攻击隐蔽性强；主流模板引擎（Twig、Freemarker、Jinja2）均有成熟利用链。

挖掘技巧与经验

  • 先做探测：提交 {{7*7}}。若页面输出 49 而不是原样文本，说明表达式被求值了。
  • 再识别引擎：${{7*7}}、#{7*7}、<%= 7*7 %>、{7*7} 分别对应不同模板家族，用多语法 polyglot 一次试探。
  • 本关是自研 PHP 模板引擎：{{ }} 内凡不是已知变量的内容，都会被丢进 eval('return ...;')。
  • 逐级利用：{{phpversion()}} 指纹识别 → {{system('whoami')}} 命令执行 → {{file_get_contents('secret.txt')}} 读文件。
  • 实战中模板注入常见于：邮件/短信模板、报表自定义字段、CMS 主题、低代码平台的表达式输入框。

本关利用步骤

  • {{7*7}} → 返回 49，确认存在 SSTI。
  • {{system('whoami')}} → 页面回显当前运行用户，确认命令执行。
  • {{system('type secret.txt')}} → 读取模块目录下的通关凭证（本关运行在 Windows 环境，请用 type 代替 cat）。
  • 若不确定当前目录，先用 {{getcwd()}} 查看工作目录，再调整读取路径。
