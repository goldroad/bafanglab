漏洞描述

JSON 注入指的是注入点位于 JSON 请求体字段中的 SQL 注入。前后端分离项目普遍使用 application/json 提交数据，开发人员往往只对表单参数（$_GET / $_POST）做过滤，却忽略了从 php://input 解析出来的 JSON 字段同样会被拼进 SQL。本关后端执行的语句是 SELECT id, username, role FROM users WHERE username = '$name'，$name 来自 JSON body 的 username 字段，字符型、单引号包裹，且 mysqli_error() 被原样输出。

漏洞危害

JSON 注入与普通 SQL 注入危害完全相同：可拖库、绕登录、读文件、写 Shell。由于 JSON 字段常被误认为"结构化数据更安全"，加上 WAF 对 JSON body 的解析与规则覆盖往往弱于表单参数，JSON 注入更容易被忽视，已成为近年来 API 漏洞的高发类型。

适用场景与判断方法

  • 接口 Content-Type: application/json，请求体形如 {"username":"admin"} → 优先检查 JSON 字段是否可注入。
  • 在 JSON 字符串值里加一个单引号 {"username":"admin'"}，若返回 MySQL 语法错误 → 确认存在注入，接着用 UNION SELECT 取数据（本关按 UNION 路径设计）。
  • 若 JSON 值是数字型（不带引号），直接在数字后追加 SQL 语句，如 {"id":1 and 1=2}。
  • 注意 JSON 转义：双引号需要写成 \"，换行写成 \n；单引号在 JSON 字符串内无需转义。
  • 若服务端用 json_decode 后强类型取字段，payload 中的特殊字符可能被截断，需换用盲注或编码绕过。

挖掘技巧与经验

  • JSON 注入的闭合方式与普通字符型注入一致：单引号闭合 + -- - 注释。
  • UNION 注入三步走：先用 union select 1,1,1 对齐列数，再用 database() 找回显位，最后把 information_schema 查到的数据放到回显位。
  • 多行结果的处理：group_concat() 合并成一行，或 limit 0,1 只取一行；不加限制会报 Subquery returns more than 1 row。
  • 很多 WAF 不解析 JSON body，直接放行，因此 JSON 注入往往能绕过基于关键字的规则。
  • sqlmap 对 JSON 注入支持良好：sqlmap -u URL --data '{"username":"admin"}' -p username --batch。

本关目标

向 JSON body 的 username 字段做 UNION 注入，读出 secrets 表中的通关凭证。完整链路：union select 1,1,1 测列数 → database() 找库名与回显位 → information_schema 拿表名、列名 → (select secret from secrets limit 0,1) 取凭证。
