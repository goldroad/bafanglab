漏洞描述

请求头注入（HTTP Header SQL Injection）指注入点位于 HTTP 请求头中的 SQL 注入。开发人员通常只对 URL 参数和表单参数做过滤，却忽视了 User-Agent、X-Forwarded-For、Referer、Cookie 等请求头同样是客户端可控的输入。很多系统把这些请求头写入数据库做访问统计、审计日志或访客识别，拼接时未过滤，从而形成注入。本关后端把 User-Agent 请求头直接拼进 SELECT id, username, role FROM users WHERE username = '$ua'，字符型、单引号包裹，且 mysqli_error() 被原样输出。

漏洞危害

请求头注入与普通 SQL 注入危害相同：可拖库、绕登录、读文件、写 Shell。由于请求头往往不经过常规的参数过滤逻辑，且很多 WAF 对请求头的检测力度弱于 URL/Body，请求头注入更容易成为漏网之鱼。尤其是 X-Forwarded-For 这类"看起来是服务端生成"的头，常被误认为可信而直接入库。

适用场景与判断方法

  • 系统记录访问日志、审计日志、访客统计时，通常会把 User-Agent、Referer、X-Forwarded-For 入库 → 检查这些头是否可注入。
  • 在 User-Agent 里加一个单引号，若返回 MySQL 语法错误 → 确认存在注入，接着用 UNION SELECT 取数据（本关按 UNION 路径设计）。
  • 常见可注入头：User-Agent、Referer、X-Forwarded-For、X-Real-IP、Cookie、X-Originating-IP。
  • 若页面不回显数据也不报 SQL 错误，可尝试时间盲注（sleep()）判断注入是否存在。
  • 请求头注入常配合日志查看页面形成"二次注入"：注入 payload 写入日志，再在日志查看页被取出执行。

挖掘技巧与经验

  • 闭合方式与普通字符型注入一致：单引号闭合 + -- - 注释。
  • UNION 注入三步走：先用 union select 1,1,1 对齐列数，再用 database() 找回显位，最后把 information_schema 查到的数据放到回显位。
  • 多行结果的处理：group_concat() 合并成一行，或 limit 0,1 只取一行；不加限制会报 Subquery returns more than 1 row。
  • 注意请求头长度限制：部分服务器限制 User-Agent 长度（如 8KB），过长 payload 会被截断。
  • 请求头中的特殊字符（如换行 \r\n）可能导致请求解析异常，注入时尽量避免。
  • sqlmap 支持对请求头注入：sqlmap -r request.txt -p User-Agent --batch。

本关目标

伪造 User-Agent 请求头做 UNION 注入，读出 secrets 表中的通关凭证。完整链路：' union select 1,1,1 -- - 测列数 → database() 找库名与回显位 → information_schema 拿表名、列名 → (select secret from secrets limit 0,1) 取凭证。
