漏洞描述

布尔盲注（Boolean-based blind SQL injection）适用于"既看不到查询结果、也看不到报错内容"的页面。攻击者构造真/假两种条件（如 and 1=1 / and 1=2），让条件的真假决定页面返回哪一种状态，再借这一点差异逐位把数据"猜"出来。速度慢，但几乎在任何数据库上都能用。

本关后端执行的语句是：SELECT id FROM users WHERE username = '$name'，字符型参数、单引号包裹、MySQL 数据库。页面只有三种反馈：存在、不存在、查询异常（SQL 报错被后端"吃掉"，只给统一提示）。

漏洞危害

盲注虽然页面没有任何回显，危害却与普通注入等同：攻击者用二分法把数据库逐字符读出来，配合 sqlmap 几小时即可完成拖库。用户数据、业务机密同样会泄露，而页面看起来完全正常，入侵行为更难被发现。若注入点位于高频接口，数据还能被自动化脚本持续批量拉取。

适用场景与判断方法

  • 先确认闭合：输入 admin'，页面出现"查询异常" → 单引号未被过滤，SQL 报错被隐藏。
  • 建立两种状态：?name=admin' and 1=1-- - 返回"存在"，?name=admin' and 1=2-- - 返回"不存在" → 布尔条件可控，可以盲注。
  • 注意第三种状态：语法错误会显示"查询异常"，别把"异常"当成"不存在"，判断脚本要按关键字或状态码区分。
  • 数据读取三步：length() 探长度 → substr() 定位字符 → ascii() 二分确定取值。
  • 页面无任何差异时（三种状态完全一致），说明该点不适合布尔盲注，改试时间盲注（sleep()）。

挖掘技巧与经验

  • 二分法最快：ascii(substr(secret,1,1))>100 每次砍一半，平均 7 次请求确定一个字符。
  • substr() 的位置从 1 开始，不是 0；写 0 会永远取不到字符。
  • payload 末尾的注释符不能省：-- -（-- 后跟空格）或 #，否则多余的单引号会导致语法错误，直接落到"查询异常"。
  • 手工先猜一个字符（例如首字符 f 的 ASCII 是 102）确认思路，再交给脚本或 sqlmap 自动化。
  • 中文/特殊字符的字面值不稳定，统一用 ascii() 比较更可靠。
  • 请求量很大，实战中注意频率限制与封禁风险；靶场里可放心跑。

本关目标

数据库为 bafanglab，目标表 secrets，字段 secret。用布尔条件逐字符取出通关凭证，先探长度，再按位置取每一位。

修复思路

  • 参数化查询（prepared statement），消除拼接入口，这是根本修复。
  • 统一响应：存在、不存在、异常返回相同的结构与相近长度，降低布尔信号（辅助手段，不能替代参数化）。
  • 对同一来源的高频请求限速、封禁，显著提高盲注的时间成本。
  • 关闭错误回显、数据库账号最小权限，并配合 WAF 做纵深防御。
