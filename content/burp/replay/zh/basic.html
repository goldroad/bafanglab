漏洞描述

重放攻击：接口依赖一次性 token/验证码防重放，但服务端并未真正"消费"该凭证（未入库、未标记、未绑定会话），导致同一请求可以被原样重复提交。

挖掘技巧与经验

  • 抓取一次性操作（转账、下单、领券、改密）的请求，发送到 Repeater 连续点两次 Send。
  • 观察第二次是否仍返回成功；对比响应中的 token 是否变化、是否提示已使用。
  • 并发重放：用 Intruder 或 Turbo Intruder 同时发送多个相同请求，测试"先检查后扣减"的竞态问题。
  • 注意时间戳、nonce、幂等键是否真的参与校验。

Token 专题：本关说的是"防重放令牌"

本关出现的 token 是防重放令牌（anti-replay token，也叫 nonce / one-time token）。它只回答一个问题：这条业务请求是不是第一次提交？它不是登录会话 token（用于识别"你是谁"）、不是 CSRF Token（用于识别"请求是不是你自愿发的"），也不是 API 里的 Bearer Token（用于接口鉴权）。三者名字都叫 token，但语义完全不同，排查时不要混为一谈。

  • 绑定对象：某一次业务操作（本关是一次转账），而不是整个会话。
  • 生命周期：一次有效，成功提交后立即作废，并换发新的 token。
  • 客户端位置：本关放在隐藏表单字段 token 里，随 POST body 一起提交到接口；也可以是请求头（如 X-Nonce、Idempotency-Key）。

与 CSRF Token 的关系（同源不同目标）

两者可以复用同一套生成机制（随机数 + 会话绑定 + 签名），但防御目标和校验时机不同，数据库/缓存中的存储与"消费"规则也必须分开实现。

对比项防重放 Token（本关）CSRF Token
防御目标同一条合法请求被重复提交（重放、并发重复扣款）第三方站点伪造用户身份发起请求（跨站请求伪造）
绑定对象一次业务操作 / 单个 nonce，请求之间不通用用户会话（session），通常整场会话通用或按表单轮换
是否可复用一次性，用过即废同一会话内通常可反复使用（部分实现按表单/页面轮换）
校验时机业务执行前校验，并在执行时原子消费（防并发双花）请求进入业务逻辑前，与会话中的值比对
校验失败结果判定为重放，拒绝本次操作判定为 CSRF，拒绝本次请求
能否共用生成机制可以共用随机数 + 会话绑定 + HMAC 签名；但存储位置、有效期与消费语义必须分开，不能用一个值同时承担两种职责

服务端如何生成、存在哪里、有效期多久

  • 随机 + 绑定 + 签名：随机串 + 时间戳 + 用户/会话 ID + 服务端密钥 HMAC，服务端可离线验签并判断时间窗。
  • 一次性序号计数器：服务端维护单调递增序号，客户端回传序号，小于等于已处理序号即视为重放。
  • 存储位置：服务端 session、Redis/缓存或数据库，记录 token 值、所属用户、创建时间、是否已用。
  • 有效期：时间窗（如 5 分钟）+ 一次性消费；过期或已用都拒绝。

本关代码的实际生成方式（对照 modules/burp/replay.php 与 modules/burp/api/ex4.php）：

// 页面初始化与接口共用同一组 session 键
if (!isset($_SESSION['used_tokens'])) { $_SESSION['used_tokens'] = array(); }
if (!isset($_SESSION['replay_token'])) { $_SESSION['replay_token'] = md5(uniqid('', true)); }

// modules/burp/replay.php：token 放进隐藏字段，随 POST body 提交
<input type="hidden" name="token" id="tkField" value="<?php echo $cur_token; ?>">

实际用的是 md5(uniqid('', true)) 生成的 32 位十六进制随机串，没有时间戳、没有 HMAC 签名、没有绑定用户或金额，只存放在当前 PHP session 的 $_SESSION['replay_token'] 与 $_SESSION['used_tokens'] 数组里，也没有过期时间。这正是靶场故意保留的简化实现。

服务端如何识别重放

  • 已用 token 黑名单 / 一次性消费：命中已用列表即拒绝。
  • 时间窗校验：token 内含时间戳，超出窗口即过期。
  • 序号单调递增：收到的序号不大于服务端已处理序号即重放。
  • 签名校验：HMAC/签名不匹配即视为伪造，直接拒绝。
  • nonce 唯一性检测：同一 nonce 第二次出现直接判定重放。

本关的判定逻辑（对照 modules/burp/api/ex4.php 实际代码，不臆造）：

$token = isset($_POST['token']) ? $_POST['token'] : '';
if ($token === '') {                       // 未带 token：直接拒绝
    echo "status=fail\n"; exit;
}

if (in_array($token, $_SESSION['used_tokens'], true)) {
    // 第二次提交同一个 token：判定为重放
    echo "status=replay\n";
} else {
    // 首次使用：记录到已用列表，并换发新 token
    $_SESSION['used_tokens'][] = $token;
    $_SESSION['replay_token'] = md5(uniqid('', true));
    echo "status=ok\n";
    echo "nextToken=" . $_SESSION['replay_token'] . "\n";
}

也就是说，本关只实现了"已用列表 + 一次性消费"这一种判定：没有时间窗、没有签名校验、没有序号，也没有校验 token 是否由服务端签发。因此任意自造的 token 只要不重复提交也能通过，这属于靶场故意留下的缺陷，正是重放/并发测试要关注的点。

正常操作 vs 重放：页面每次转账成功后会同步更新隐藏字段并显示新 token，正常点击不会误判；只有把同一条 POST 请求（同一个 token）原样重发，才会看到 status=replay 与"检测到重放攻击"的提示。
